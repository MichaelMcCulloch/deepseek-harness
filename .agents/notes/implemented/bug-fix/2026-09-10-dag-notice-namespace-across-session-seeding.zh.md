# Agent Note: DAG 通知命名空间跨会话播种

Status: implemented

[English](2026-09-10-dag-notice-namespace-across-session-seeding.md) | 中文

## 问题

每次被接受的 DAG 变更都会追加一个完整的 `dag/state` 快照，其中携带 `noticeNamespace`，通知 id 由该值连同图代数以及节点代数或 wave id 组合而成。确定性的通知 id 使恢复流程能够在重新注入通知之前比对待处理 inbox 条目与已认领 inbox 会话事件，从而在会话重新打开后仍保持幂等投递。

服务曾用当前调度器智能体 id 标记每次写入，而 reducer 要求该值与已折叠进状态的命名空间相等。从另一个会话播种而来的会话会继承该会话的 `dag/state` 快照，其命名空间是源会话 id，而当前智能体 id 是新会话 id。此后每次 `dag_write` 都以 `dag-invalid-notice-namespace` 失败，被继承的图在该会话余下的生命周期内无法接受新节点或修改。读取仍然成功，因此图看起来仍然可用，而每次写入都被拒绝。

## 决策

`DagService.write` 从已折叠的状态解析命名空间，仅在首次声明之前回退到当前智能体 id：

```ts
noticeNamespace: this.state(agent)?.noticeNamespace ?? agent.id,
```

首次声明确定命名空间；此后的每次写入，无论在声明它的会话中运行，还是在由该会话播种出的会话中运行，都保留该值。reducer 的稳定性规则不变——状态值在首次写入之后永不改变命名空间——因此通知 id 保持稳定，被继承的投递记录也仍然可以匹配。

## 曾考虑的替代方案

**用当前智能体 id 标记每次写入并让 reducer 采纳它。** 拒绝。在图的运行中途采纳新命名空间，会让状态中已记录的通知继续携带基于旧命名空间构建的 id，而后续通知使用新命名空间。稳定性规则正是为防止这种分裂而存在，且两套 id 空间将不再可用于比对去重。

**从会话的 fork 源推导命名空间，而不是从状态读取。** 拒绝，因为多余。在被播种的会话中，折叠出的命名空间本身就是源会话 id，因此从状态读取会得到相同的值，却少一层依赖，同时还能覆盖源已无法解析的会话。

**放宽 reducer，接受任意非空命名空间。** 拒绝。该检查正是通知 id 在重新打开后保持确定性的原因；接受任意值会让调用方重新标记一个活动图，从而悄然破坏恢复所依赖的幂等重注入。

## 后果

在会话播种之前声明的图在播种之后仍可修改，且其通知 id 与其被继承快照已引用的 id 完全一致，因此恢复流程不会重新注入源会话已经投递过的通知。

代价是，由同一源播种出的两个会话会从同一命名空间推导通知 id。id 在单个图内保持唯一，而去重是按会话针对各自 inbox 进行的，因此共享命名空间不会以冲突的形式显现。

在全新会话中的首次声明仍然采用该会话的 id，因此在播种之后声明的图拥有自己的命名空间。

## 验证

`service.spec.ts` 固定了两条分支：首次声明把命名空间固定为调度器会话 id；持有带外部命名空间继承快照的会话在下一个修订号上修改图时保留该命名空间。第二个测试在本变更之前以 `dag-invalid-notice-namespace` 失败，在变更之后通过。
