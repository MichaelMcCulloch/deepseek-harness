# Agent Note: 撕裂尾部修复只需一个持久步骤

Status: implemented

[English](2026-09-21-atomic-torn-tail-replacement.md) | 中文

## 问题

JSONL 后端通过恢复撕裂的最后一个 Zstandard 帧中完整的 JSONL 记录来服务它：frame 扫描报告该尾部的起始字节，读取方返回这个不完整帧已经承载的全部完整记录。随后写句柄必须把这份逻辑日志落成物理日志，而它此前在 `persistContiguous`（`packages/session/session-persistence-jsonl/src/storage.ts`）中分两个持久步骤完成：截断撕裂字节并 fsync，然后追加已恢复的记录。

两步之间的崩溃会销毁一次读取已经提供过的事件。这些记录存在于读取它们的进程的内存日志中，DAG 折叠了它们并据此运行以它们为键的 effect，而下一次重新打开只看到被截断的前缀——比一次已完成的读取所观察到的日志更短，接续的写入方因此被拒绝：`packages/session/session-persistence-jsonl/tests/zstd.spec.ts` 复现出重新打开后提供 seq 0..5 而非已提供过的 0..7，而继续于 seq 8 的写入方以 `append seq mismatch for "repair-crash-continue": expected 6 at index 0, got 8` 被拒绝。

这个窗口比它所称的崩溃更宽。`truncateTornTail` 在自己的 fsync 完成之前就已销毁了恢复出的记录，因此截断本身的 fsync 失败也会丢失它们，而追加路径不再有任何状态能让重试知道该恢复什么。[DAG 转换验证提案](../../proposed/testing/2026-09-21-dag-transition-verification.zh.md)记录了这个缺陷与两种候选设计；本笔记记录最终交付的那一种。

## 决策

修复与紧随其后的批次作为**对日志文件的一次持久替换**发布，发布它的 rename 即提交点。

`JsonlHandleStorage.persistBatch` 以参数接收待处理的修复。带修复时，`JsonlSessionPersistence.replaceTornTail`（`packages/session/session-persistence-jsonl/src/index.ts`）用追加路径所用的同一个逐批编码器编码产物的完整前缀字节、从其撕裂尾部恢复出的完整记录以及到达的批次，把它们写入日志旁一个已同步的替换文件，将该文件 rename 覆盖日志，并在 POSIX 上 fsync 所在目录。Windows 通过 `replaceFileWin32` 发布，该函数加入 `src/win32.ts`，使用 `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`：这正是修复所需的替换语义，并带有本包发布新文件时已经依赖的 write-through 完成保证。`truncateTornTail`、私有的 `repair` 以及那个两步序列都已移除；`persistContiguous` 只在其唯一一次存储调用完成后才清除修复状态，因此一次拒绝会重试整个修复。

### 每种失败会留下什么

替换文件在触碰日志之前写入并 fsync，而 rename 是原子的，因此在 rename 之前的任何失败都会让撕裂产物与读取当时所见逐字节相同，并让重试能够重新编码同一个替换。初始 `open(..., 'wx')`、写入或临时文件 fsync 的失败都会移除这个未发布的替换。

rename **之后**的目录 fsync 失败会通过 logger 报告，而不会让 append 拒绝。拒绝比命名空间变更未经确认更糟：调用方会重试该批次，保留下来的修复会在已包含这些事件的文件之上重新编码恢复记录与该批次，最终日志把其中每条事件都存储两次——这是损坏，而不是更窄的持久性窗口。替换本身的字节已经 fsync，因此残留风险只是 rename 与目录 fsync 之间断电，那会把目录项回退为撕裂产物，而不会丢失任何东西。

### 哪些写入路径会带修复

修复只在一个地方被装载：对一个已存日志带撕裂尾部的会话执行写打开。该打开读取的是已存在的产物，因此只要修复待处理，`isMaterialized` 就恒为 true，且修复路径从不物化会话——`create` 与读打开都不带修复，`persistHeader` 不写事件，而不带修复的 `persistBatch` 走与之前相同的追加或物化路径并存储相同的字节。修复分支忽略 `isMaterialized`，而不是对一个不可达的组合分支；针对缺失产物的修复会在读取前缀时失败，而不是静默创建一个。

### 替换文件

替换路径是代际日志路径加上 `.repair.tmp`（`src/format.ts` 中的 `repairReplacementPath`）。该后缀使它落在 `parseGenerationLogFilename` 之外，因此代际发现、列举与相反编码检查都不会把它读作产物——崩溃残留对每个读取方都不可见。名字固定而非随机，是因为整个修复期间持有该会话的跨进程写锁：每个代际最多只会有一份残留，之后的修复会覆盖它，而写打开会在取得锁之后、任何 append 从该路径发布之前立即清除它。创建使用 `wx`，因此残留绝不会被当作符号链接跟随，也不会有无关的写入方被覆盖。

## 后果

一次成功修复的磁盘结果与两步协议产出逐字节相同——相同的前缀字节，后接每批一个编码帧——`zstd.spec.ts` 以编码器自身的输出为基准断言了这一点，原始行编码也包括在内：它的撕裂尾部不恢复任何记录，因此只编码批次帧。永不撕裂的日志仍然走未改动的 `appendLines`。

修复现在读取产物的前缀而不是就地截断，因此撕裂读取后的第一次写入要多付一次完整读取与一次完整重写，而该文件本来就会被读取路径整体加载。修复只发生在崩溃残留时，而替代方案——就地覆盖撕裂后缀——无法在写入中途崩溃后存活。

声明面缩小了：`truncateTornTail` 从提供方本地的存储接口与服务中移除，两个相关的可选句柄状态字段合并为一个 `TornTailRepair` 值，使「有截断点却没有其恢复记录」不可表达。

覆盖：`zstd.spec.ts` 钉住崩溃窗口（被中断的修复必须让一次读取已提供的事件仍可恢复，重新打开的写入方必须完成修复且每条事件只存储一次）、未发布替换的清理、已发布替换的目录 fsync 警告，以及残留。`win32.spec.ts` 钉住 `replaceFileWin32` 的标志位与错误映射。既有的持久性、撕裂尾部与失败重写重试用例不变且通过，本包保持逐文件 100% 覆盖率。

## 考虑过的替代方案

**由下一次打开重新应用的修复 sidecar。** 提案记录的另一种设计：把恢复出的记录写入 sidecar，让下一次打开在截断前应用它。它会增加第二个持久产物，其发布需要自己的原子协议，使读打开成为修复的参与者，并留下 sidecar 与日志就谁具权威性产生分歧的状态。以一个 rename 替换日志则让修复对读取方不可见，也不留下第二个事实来源。

**像首次物化那样通过 `link()` 加 `unlink()` 发布。** 物化协议刻意无法覆盖已存在的路径，而修复总是替换一个已存在的文件——日志存在，这正是存在撕裂尾部的原因。`link()` 恰恰会在需要修复时以 `EEXIST` 失败。

**就地重写撕裂后缀。** 从撕裂帧起始处写入新帧可保留文件 inode 且无需第二个文件，但写入中途崩溃会留下一个不完整的帧，其起始字节并非帧边界；而先截断文件则会重新引入本决策所移除的那个破坏性步骤。

**不再从撕裂帧恢复记录，使截断无物可失。** 只提供完整帧会让两步修复在构造上就是安全的，代价是丢弃崩溃进程已经发出并刷入该不完整帧的事件——尾部的每一条完整记录都会被丢弃，resume 看到的日志将短于崩溃前那次已完成读取所见。这种已提供历史的倒退比它所规避的协议问题更大。

**用 `fs.copyFile` 复制后再追加。** 字节相同，却要对产物多走一遍完整流程，而且没有任何「写临时文件再 rename」尚不具备的性质。

**rename 之后的目录 fsync 失败时拒绝该 append。** 调用方会重试该批次，而保留的修复会把恢复记录与该批次存储第二次；未经确认的目录项是更小的暴露面。

**随机替换文件名，与 `writeSyncedTempFile` 保持一致。** 随机名无法被寻址清理，因此残留会一直累积到有人扫描会话目录为止；固定名是安全的，因为修复在会话写锁下运行，且写打开会先清除残留。
